# 设计决策摘要

本文档保留已经影响当前实现的关键决策。原始分析过程已删除，避免过时方案继续被误用。

## 辅助码必须使用 `[`

曾尝试把无引导的三字母输入解释为“两码双拼 + 一位辅助码”。该方案存在不可消除的歧义：第三个字母也可能是下一双拼音节的开头。

18键共键会进一步放大分支数量。例如每个共键位置可能展开为两个字母，音码、辅助码和下一音节边界同时模糊时，候选和解析都不稳定。

另一个问题是 `table_translator@custom_phrase_3_code` 可直接产生三码候选，绕过 script translator 的 speller 规则。仅修改 algebra 不能可靠禁止无引导辅助码。

最终决策：

- 纯双拼按两码分段。
- 辅助码只在 `[` 后解析。
- 不启用无引导三码辅助码 Processor/Filter。

## 保留 algebra 模糊，使用 Lua 做精确过滤

尝试过完全由 Lua Translator 动态生成候选，但会重复 Rime 的词典、造句、用户词频和语言模型能力，实现与维护成本过高。

最终采用混合架构：

- algebra 在部署时生成共键模糊 prism。
- Processor 记录滑动精确位置。
- 原生 translator 负责候选、造句和用户词典。
- Filter 使用 ReverseLookup 做运行时精确约束。

## 精确输入使用大写作为传输标记

Trime 点击共键发送小写，左右滑动发送对应大写。大写只作为键盘层到 Lua Processor 的标记，Processor 随即转成小写，因此不会改变词典编码格式。

## 禁用飞键

原 Moqi 飞键规则与18键共键模糊叠加后会扩大错误匹配，例如 `ww/wi/wo` 的优先关系变得不可预测。Android 18键方案禁用飞键，优先保证共键规则可解释。

## 移除六码上限

`speller/max_code_length: 6` 会截断三个音节以上的连续双拼，并影响部分选词后的剩余音节解析。当前方案不设置该上限。

## 候选过滤按区间执行

精确位置属于完整输入的字符位置，而候选可能只覆盖前缀或剩余片段。Filter 必须使用候选 `start/end`：

- 覆盖精确位置的候选执行过滤。
- 包含 `[` 的候选执行辅助码过滤。
- 与精确位置无关的前缀候选原样保留。

这避免 `nihx` 中后半段精确输入错误删减前缀 `ni` 的单字候选。

## 多音字读取全部反查编码

ReverseLookup 对多音字返回空格分隔的多组编码。只检查第一组会让其他读音在精确输入时消失。当前 Filter 缓存全部编码，任意一组完整匹配即可保留。

## Android 部署采用定向缓存清理

快速部署只删除当前18键方案的 schema、prism 和主题构建产物，避免旧缓存继续运行；不清理用户词库和其他方案数据。上传后先验证核心文件非空，再广播部署。

## 不在配置层修改 Trime 窗口状态机

展开候选窗口在部分选词后随退格重新打开，是 Trime 3.3.11 的窗口状态机行为。修改 Rime `paging_mode` 或主题候选游标无效；Lua 接管退格会改变标准 segment 回退语义。当前决定是不做高风险 workaround，等待上游修复。
